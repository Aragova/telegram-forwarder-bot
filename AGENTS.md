## Порядок проверок PR

- Обязательные проверки: CI проекта (тесты, PostgreSQL, Smoke, Architecture), SonarCloud, Gemini Code Assist и Codex; если сервис недоступен из-за квоты, явно зафиксировать исключение владельца. Проверять актуальный HEAD, не обходить защиту веток.
- CodeRabbit: профиль chill, автоматическое ревью отключено. Один ручной полный обзор (`@coderabbitai full review`) после стабилизации кода и прохождения основных проверок. После исправлений — только инкрементальный обзор (`@coderabbitai review`) изменённого HEAD при необходимости. Не повторять полный обзор без существенного изменения архитектуры или явного поручения владельца.
- Оценивайте замечания по фактическому ущербу, а не метке ревьюера. P0: потеря/повреждение данных, нарушение tenant-изоляции или безопасности, неконтролируемые дубли, критический отказ. P1: доказуемая регрессия основного сценария, остановка очереди, значимый эксплуатационный риск. P0/P1 блокируют merge; подтверждать по текущему коду и воспроизводимому сценарию, исправлять минимально с регрессионным тестом.
- P2/P3: малозначимые редкие сценарии без существенного ущерба, локальные оптимизации, стиль, дополнительные тесты без выявленного дефекта. Не блокируют merge; зафиксировать остаточный риск в PR или отдельной задаче. Редкость сама по себе не снижает приоритет потери данных, дублей или нарушения безопасности.
- Не расширять область PR ради старых не связанных с изменениями дефектов: зарегистрировать отдельную задачу; если дефект делает текущий PR небезопасным, считать блокером. Повторные комментарии о том же сценарии сверять с уже внесёнными исправлениями.
- Критерий завершения: обязательные проверки актуального HEAD прошли, реальные P0/P1 устранены, остаточные риски перечислены и решение о merge соответствует разрешению владельца. Нулевое количество замечаний не является целью. Не закрывать неисправленное замечание под видом исправленного.
