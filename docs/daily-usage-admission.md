# Дневной учёт и атомарный допуск публикаций

- Ключ учёта — tenant_id и календарный день UTC. Записи предыдущих дней не обнуляются. Новый день имеет собственную запись; рестарт не изменяет статистику.
- Предварительный лимит планировщика остаётся подсказкой, а окончательный допуск проверяется в PostgreSQL внутри take_due_delivery_and_create_job. Фактическая подписка выбранного tenant проверяется под блокировкой строки; UPSERT по ключу tenant/day условно увеличивает jobs_count. Конкурирующие правила одного tenant не смогут использовать один оставшийся слот.
- Увеличение счётчика, создание job, перевод доставок в processing и резервирование времени коммитятся совместно. При дубликате, отказе, исключении или rollback повторного списания нет. Альбом учитывается как одна задача. OWNER остаётся без ограничения, но его статистика сохраняется.
- Воркеры обычных доставок проверяют подписку, а не уже списанный лимит создания jobs. Повторы и видео-стадии не требуют новой квоты jobs. Проверка video_count и учёт завершённых видео не изменены; конкурентный лимит видео и атомарность его финализации — отдельная задача. Рекламные задания сохраняют прежний контракт.
- Старый неатомарный fallback для тестовых/совместимых репозиториев остаётся; production использует PostgreSQL.
- Схема БД не меняется. Исторические счётчики, которые могли быть обнулены предыдущими версиями, не восстанавливаются догадками.
- Покрытие: рестарт с выключенной пересылкой, UTC rollover, отсутствие двойного списания планировщиком, выполнение последней разрешённой задачи, параллельный последний слот, rollback, альбом, неактивная подписка.
