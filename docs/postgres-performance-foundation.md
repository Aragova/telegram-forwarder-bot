# Оптимизация PostgreSQL (P1.1–P1.5)

База аудита: архив main a6c3b21. Схема БД, доставка, lease/ledger,
пересканирование, режимы repost/video и all не изменяются.

## P1.1 — сводка карточки и позиции

Именованный серверный курсор читает максимум 512 сырых строк за порцию.
В repost не передаётся content_json; не читаются тексты ошибок, попытки и
прочие поля, не участвующие в сводке. В video сохраняется существующий
Python-декодер TEXT-поля (в том числе устаревший/битый JSON).
Общий builder строит только компактные счётчики, а не полные векторы
доставок/постов и payload. Позиция и карточка используют одну сводку.
Полные элементы для rollback/start-from остаются прежними.

Это точный пересчёт: PostgreSQL всё ещё читает все доставки данного правила,
а компактные группы занимают O(число логических элементов) памяти.
Кэш или новый persisted ledger не вводятся, чтобы не создать второй источник истины.

## P1.2 — каталог

get_rule_catalog_page возвращает только страницу (обычно 10 строк), total,
active, фактический номер страницы, папки текущей страницы и валидные выбранные
ID. Счётчики, фильтрация и LIMIT/OFFSET выполняются одной SQL-командой.
Номер страницы ограничивается после удаления правил. Папки, поиск, добавление
существующих правил, массовый выбор и старые страницы используют один контракт.
Глобальный список администратора и его tenant/legacy workspace разделены.
Каналы связываются по tenant, chat, topic и типу. Поиск #ID точный, текстовый
поиск — PostgreSQL lower/strpos, символы % и _ буквальные. Unicode-регистр
зависит от collation PostgreSQL (не полный Python casefold для всех письменностей).
Для одноразового чтения всей совокупности (например scheduler) прежние методы
get_all_rules/get_rules_for_tenant сохраняются.

## P1.3 — статистика

Восемь последовательных COUNT заменены одним запросом, сканирующим deliveries
и routing по одному разу. Счётчики точные, без TTL. Пользовательский «Живой
статус» больше не строит карточки всех правил и читает физические pending/faulty
в своём tenant; раньше экран обращался к отсутствующим pending_count/faulty_count.

## P1.4 — соединения

Локальные признаки closed/broken вместо SELECT 1 на каждую операцию.
При неудавшемся rollback соединение выбрасывается. Явный ping остаётся.
Сетевой обрыв незаметный libpq до запроса может сделать первый запрос
неуспешным; автоматический повтор транзакции запрещён.

## P1.5 — исполнение

Четыре выделенных UI DB-потока в процессе bot/all. Частные сообщения и
callback получают UI lane через middleware. Фоновые задачи и rescan
не наследуют UI lane; scheduler/worker остаются на существующем default pool.
Контекст копируется, в том числе fencing. Слот удерживается до окончания
синхронного вызова, даже при отмене ожидающего coroutine. После asyncio.run
UI executor полностью завершается перед закрытием соединений.

## Проверки и ограничения

Регрессии сравнивают полные/компактные элементы, проверяют tenant/owner ACL,
папки, поиск, страницу после выхода за диапазон, агрегаты и изоляцию UI lane.
Реальные SQL-контракты выполняются в disposable PostgreSQL CI.
Перед rollout проверить бюджет max_connections (до 4 дополнительных
соединений на UI-процесс), длительность карточек и EXPLAIN ANALYZE на
репрезентативной копии production. Не обещать O(1) exact count или
отсутствие SQL lock contention: отдельный executor их не устраняет.
