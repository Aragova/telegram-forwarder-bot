# P0.12 / P0.9: восстановление пересканирования и shutdown

## Совместимость

Только два nullable поля routing: rescan_operation JSONB и rescan_lease_until TIMESTAMPTZ.
Применяются существующим ADD COLUMN IF NOT EXISTS при инициализации.
Нет обновления существующих строк, массового пересканирования, сброса позиций,
переиндексации, новых кнопок или дополнительных сервисов.

## Протокол

UI запускает тот же fresh/keep алгоритм. Под блокировкой routing в одной
транзакции сохраняются режим, исходный статус, источник/получатель/tenant,
курсор первого незавершённого логического элемента и watermark, actor и phase.
Старые job leases отзываются существующим способом. Парсер использует прежние
правила чтения Telegram и save_post_batch, но каждый пакет несёт owner token.
При потере владения старый парсер не может записать даже исходный пакет.
Владелец обновляет аренду каждые 20 секунд; срок аренды 120 секунд по часам БД.
Просроченный token не возобновляется. Новый token выдаётся атомарным UPDATE.
Старая операция не может зафиксировать очередь после смены token.

При перестройке существующая транзакция устанавливает phase=rebuilt вместе с
новыми delivery IDs. После неоднозначного ответа или рестарта recovery читает
именно этот marker, а не исторический rescan_queue_built. Для rebuilt только
снимает блокировку. Для scanning повторяет полное чтение с исходным курсором.
После трёх попыток без подтверждённой перестройки правило остаётся выключенным,
появляется audit event, а существующая кнопка пересканирования доступна.
Сканирование при recovery выполняется по одному правилу; успешный recovery
не редактирует старое Telegram-сообщение, чтобы не перезаписать чужой экран.
Неизменённые правила вообще не выбираются. Состояние изменённого маршрута
при завершении не активируется автоматически. Длительный FloodWait
обслуживается существующим транспортом, а heartbeat продолжает работать.

Старые блокировки без metadata не восстанавливаются автоматически.
После полного остановочного обновления всех ролей существующая кнопка
пересканирования может явно заменить такую блокировку; правило остаётся
выключенным, поскольку его прежний статус неизвестен. Режим fresh по-прежнему
требует одноразовое подтверждение. Не смешивать версии в процессе rollout.

## Shutdown

Начало shutdown запрещает новые UI jobs и worker generations. Scheduler
отменяется первым: его уже начатый tick завершает текущую транзакцию и не
принимает следующее правило. Долгие UI/rescan задачи отменяются и join,
а незавершённые операции остаются в БД. Worker и campaign drain при
неполном завершении повторяется; ресурсы не закрываются и main не возвращается
до завершения. Существующий systemd TimeoutStopUSec остаётся внешней
границей; SIGKILL при аварии не является подтверждением результата Telegram.
Долговечные receipts и ledger остаются источником восстановления доставки.

Проверить действующий systemd override (SIGINT, TimeoutStopUSec=720s) перед
выкаткой. Не применять старый код одновременно с новым. Не требуется
пересканировать нормальные правила или обновлять их индексы.
