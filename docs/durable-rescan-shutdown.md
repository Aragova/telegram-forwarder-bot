# P0.12 / P0.9: восстановление пересканирования и shutdown

## Совместимость

Только два nullable поля routing: rescan_operation JSONB и rescan_lease_until TIMESTAMPTZ.
Применяются существующим ADD COLUMN IF NOT EXISTS при инициализации.
Нет обновления существующих строк, массового пересканирования, сброса позиций,
переиндексации, новых кнопок или дополнительных сервисов.

## Протокол

UI запускает тот же fresh/keep алгоритм. Под блокировкой routing в одной
транзакции сохраняются режим, исходный статус, источник/получатель/tenant,
курсор первого незавершённого логического элемента и watermark, actor и phase.
Старые job leases отзываются существующим способом. Парсер использует прежние
правила чтения Telegram и save_post_batch, но каждый пакет несёт owner token.
При потере владения старый парсер не может записать даже исходный пакет.
Владелец обновляет аренду каждые 20 секунд; срок аренды 120 секунд по часам БД.
Просроченный token не возобновляется. Новый token выдаётся атомарным UPDATE.
Старая операция не может зафиксировать очередь после смены token.

При перестройке существующая транзакция устанавливает phase=rebuilt вместе с
новыми delivery IDs. После неоднозначного ответа или рестарта recovery читает
именно этот marker, а не исторический rescan_queue_built. Для rebuilt только
снимает блокировку. Для scanning повторяет полное чтение с исходным курсором.
После трёх попыток без подтверждённой перестройки правило остаётся выключенным,
появляется audit event, а существующая кнопка пересканирования доступна.
До подтверждённой перестройки обычное включение запрещено: неполный пакет
мог сохранить новые посты без deliveries. Повторный перескан по существующему
меню сверяет Telegram и атомарно перестраивает очередь. После этого включение
работает как обычно. На экране ожидания доступен только переход к карточке.
Сканирование при recovery выполняется по одному правилу; успешный recovery
не редактирует старое Telegram-сообщение, чтобы не перезаписать чужой экран.
Неизменённые правила вообще не выбираются. Состояние изменённого маршрута
при завершении не активируется автоматически. Длительный FloodWait
обслуживается существующим транспортом, а heartbeat продолжает работать.

Старые блокировки без metadata не восстанавливаются автоматически.
После полного остановочного обновления всех ролей существующая кнопка
пересканирования может явно заменить такую блокировку; правило остаётся
выключенным, поскольку его прежний статус неизвестен. Новые низкоуровневые
вызовы без actor_id получают отличимый local-token и не могут вытеснять
retry_pending; UI не может вытеснить такой живой owner. Production UI всегда
передаёт actor_id. Режим fresh по-прежнему
требует одноразовое подтверждение. Не смешивать версии в процессе rollout.

## Shutdown

Начало shutdown запрещает новые UI jobs и worker generations. Scheduler
отменяется первым: его уже начатый tick завершает текущую транзакцию и не
принимает следующее правило. Сигналы остановки UI/rescan отправляются до ожидания любого join.
Producer joins, worker/campaign drain и сохранение publication evidence
выполняются параллельно. Уже начатые транзакции и дочерние задачи
присоединяются; ресурсы не закрываются и main не возвращается до завершения. Существующий systemd TimeoutStopUSec остаётся внешней
границей; SIGKILL при аварии не является подтверждением результата Telegram.
Долговечные receipts и ledger остаются источником восстановления доставки.

Проверить действующий systemd override (SIGINT, TimeoutStopUSec=720s) перед
выкаткой. Не применять старый код одновременно с новым. Не требуется
пересканировать нормальные правила или обновлять их индексы.


Shutdown waits directly on remaining worker/campaign task completion after the initial bounded drain. It does not re-cancel their cleanup. The recovery supervisor uses a stop event to wake immediately when idle; its current rescan child is cancelled and joined separately. The periodic database expiry check remains necessary because leases may expire without any local notification. Manual worker stop retains its existing bounded behavior.

Запись аудита автоматического recovery выполняется в транзакции снятия блокировки. Повтор после потерянного ответа commit не дублирует audit. Пока длятся producer joins и worker/campaign drain, отдельная попытка сохранения только volatile publication evidence повторяется периодически; финальная проверка перед закрытием Telethon сохраняется. Уже долговечные записи SQLite/журнала не читаются и не очищаются этим flusher: их replay остаётся штатным на следующем старте. Начатая запись присоединяется до закрытия ресурсов; пятисекундный интервал не является жёстким дедлайном дискового I/O.

Пакеты истории с rescan owner сохраняют исходные посты, но не создают новые deliveries для пересканируемого правила до атомарной перестройки. Остальные правила и live ingest работают как прежде. Результат release фиксируется в существующем audit_log вместе с освобождением владельца, привязан к хешу token и возвращается при повторе после потерянного commit. Для TCP-подключений PostgreSQL заданы keepalive (30/10/3) и tcp_user_timeout=60000 мс; это сокращает обнаружение оборванной сети, но не гарантирует срок ответа работающего TCP peer при зависшем серверном приложении.

При исчерпании попыток обоих режимов операция сохраняется в существующем JSONB как retry_pending без владельца и аренды; это не автоматическая задача. Явный keep после keep с тем же tenant и маршрутом использует исходный курсор. Fresh использует свой штатный алгоритм. До успешной перестройки включение, смена позиции, rollback и очистка очереди не снимают этот барьер; смена режима не очищает marker. Захват просроченных операций пропускает занятые строки routing (SKIP LOCKED). Квитанция освобождения обязательна для каждого токена, даже после получения нового владельца. Rebuilt освобождаются независимо от единственного фонового чтения истории. Один flusher обслуживает параллельные producer joins и drain воркеров и кампаний: остановка одного runtime не ждёт завершения другого. Все drain присоединяются до закрытия клиентов, даже если один завершился ошибкой; финальная проверка остаётся перед закрытием транспорта.


## Откат версии

Перед переходом на код без durable recovery необходимо завершить все операции
scanning/rebuilt поддерживаемой версией и проверить отсутствие активных
владельцев и retry_pending. Не очищать token или marker вручную и не включать
правило с неподтверждённой очередью. Если проверка не проходит, отложить downgrade.
